# Связь правил с бизнес-требованиями

Источником для ссылок в правилах служит файл
`Бизнес-требования для работы с бенефициарами номинальных счетов.docx`.

- `SHA-256`: `521375fedfffed655736cadc6d13bd564d55aef68777cc8a3f96d24bc6235578`;
- последняя запись в истории изменений документа: версия 14 от 20 октября 2025 года;
- разделы и пункты извлекаются из структуры DOCX и текста вложенных таблиц;
- `page` — справочная страница начала раздела в текущей выгрузке;
- `pageKind: "section-start"` прямо указывает, что страница не является устойчивым идентификатором.

## Формат метаданных

Spec RC.7 не допускает верхнеуровневый `rule.meta`. Авторские сведения можно
хранить в `rule.issue.meta`. Rules v4 включает их в `sourceHash` и без изменений
возвращает в найденной ошибке.

```json
{
  "issue": {
    "level": "ERROR",
    "code": "FL.INN.LENGTH_12",
    "message": "ИНН ФЛ должен содержать ровно 12 цифр",
    "meta": {
      "requirements": [
        {
          "document": "Бизнес-требования для работы с бенефициарами номинальных счетов.docx",
          "documentSha256": "sha256:521375fedfffed655736cadc6d13bd564d55aef68777cc8a3f96d24bc6235578",
          "section": "2. Набор полей для физических лиц (ФЛ)",
          "item": "п. 1 — ИНН",
          "page": 13,
          "pageKind": "section-start"
        }
      ]
    }
  }
}
```

Для общего правила перечисляются все таблицы, к которым оно относится. Если
конкретное ограничение сохраняет действующий API-контракт, но не записано в
бизнес-требованиях отдельно, `explanation` объясняет это одним предложением.

Условия, сценарии и справочники не создают ошибок выполнения. Поэтому у них
нет `issue` и, следовательно, нет `issue.meta`; их назначение описывает
`manifest.catalog.artifacts`.

## Зафиксированные расхождения

- Бизнес-требования показывают даты как `ДД.ММ.ГГГГ`, а JSON API и правила
  используют `YYYY-MM-DD`.
- В строке ОГРНИП бизнес-требования указывают 13 цифр. Правило сохраняет
  стандартный 15-значный формат ОГРНИП действующего API.
- `$context.currentDate`, номер номинального счёта, КПП иностранного ЮЛ и часть
  детализации регистрирующего органа не выделены отдельными строками таблиц.
  Для таких правил дана ссылка на общий пункт о проверках и пояснение.
- Пункт 9 раздела ЮЛ задаёт юридический адрес, но не перечисляет минимальный
  набор полей JSON API. Обязательность `regionCode`, `postalCode`, `city` или
  `locality`, `streetType`, `street`, `house` только для регистрации
  `UL_RESIDENT` уточнена в задаче от 2026-09-03; это указано в `explanation`
  новых правил. Набор вводится пакетом `2.0.0`, а не приписывается исходному
  тексту БТ. Проверка непустой строки отделена от распознавания адреса в ЦФТ.

С версии `2.0.1` пункты о налоговом резидентстве ФЛ и ИП применяются одинаково
в четырёх полных проверках: `foreignTaxResident`, `usTaxResident` и
`usResident` должны присутствовать и иметь логический тип. Это исправляет
неполное подключение уже существующих общих правил и не меняет трактовку
значений `true` и `false`.

С версии `2.0.2` запрет почтового адреса в США проверяется по отдельному полю
`beneficiary.contacts.postalAddressCountryCode`. Решение опирается на
действующий договор ФЛ/ИП: код страны имеет формат ISO 3166-1 alpha-2, а
свободный текст `postalAddress` не используется как нормативный источник
страны. Код ошибки `BEN.CONTACTS.POSTAL.NOT_US` сохранён.

С версии `2.0.3` этот принцип применяется ко всем свободным строкам ФЛ и ИП.
`beneficiary.fl.birthPlace` и
`beneficiary.tax.foreignTaxResidency.address` не используются для определения
США. Исходное БТ содержит текстовые ограничения для этих полей, но не задаёт
однозначного способа распознавания страны. Текущий договор реализации использует
только структурированные коды `beneficiary.fl.citizenshipCode`,
`beneficiary.contacts.postalAddressCountryCode`,
`beneficiary.tax.foreignTaxResidency.countryCode` и явные логические признаки
США. Это решение разработки, а не новая формулировка исходного БТ.

С версии `2.0.4` регистрация `FL_NONRESIDENT` согласована с предметным
определением типа по гражданству и адресным контрактом. Российское гражданство
отклоняется обычной ошибкой данных, `US` сохраняет отдельный регуляторный
отказ. Код страны регистрационного адреса обязателен: `RU` включает проверки
ФИАС-структуры, разрешённый иностранный код требует `fullAddress`, `US`
отклоняется. Проверки связаны с п. 7 и п. 26 раздела ФЛ исходного документа;
выбор alpha-2 и маршрутизация по структурированному коду относятся к
действующему техническому контракту.

С версии `2.0.5` регистрационный адрес `FL_RESIDENT` допускает только код
страны `RU` и российскую ФИАС-структуру. Более позднее уточнение Владислава от
3 июня 2026 года отделяет этот контракт от `FL_NONRESIDENT`: строковый
иностранный адрес применяется только для нерезидента. Допустимая иностранная
страна в resident-контуре возвращает обычную ошибку данных, а `US` сохраняет
отдельный регуляторный отказ.

С версии `2.0.7` иностранный налоговый адрес и почтовый адрес необязательны при
регистрации `FL_NONRESIDENT` и `IP_NONRESIDENT` и могут отсутствовать
одновременно. Это уточнение основано на подтверждении Владислава от 9 июня
2026 года: при отсутствии адреса мерчант не передаёт параметр и не подставляет
строковое значение «Отсутствует». Структурированные налоговые данные не
ослаблены: страна, иностранный ИНН или причина его отсутствия остаются
обязательными, код страны `US` по-прежнему отклоняется.

С версии `2.0.8` минимальный контакт `FL_NONRESIDENT` включает
`beneficiary.contacts.foreignPhone` вместе с российским телефоном и электронной
почтой. Это согласует общее требование пп. 28–30 с предусмотренным п. 36
иностранным телефоном при отсутствии российского. Специальная обязательность и
проверка международного формата не ослаблены; остальные типы бенефициаров не
изменены.

`scripts/verify-package.mjs` проверяет наличие описаний всех полей, метаданных
всех правил с ошибками, точного хэша документа и примеров для каждого кода.
